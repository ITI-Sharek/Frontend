## 2. Top-Level Folder Responsibilities

| Folder | Responsibility | Must NOT contain |
|---|---|---|
| `routes/` | TanStack Router route definitions, route shells, route-level composition, loaders, redirects, pending/error composition | Business logic, raw API calls, reusable components |
| `modules/` | Domain/business logic, one folder per feature | Lateral feature imports, generic UI primitives |
| `shared/` | Feature-agnostic UI and generic utilities used by multiple features | Anything that imports from `modules/*` |
| `providers/` | App-wide singleton React context providers, mounted once from `routes/__root.tsx` | Business logic |
| `lib/` | Configured third-party clients and framework glue | React feature components/hooks |
| `services/` | Cross-cutting services not owned by one feature | Feature-specific API calls |
| `hooks/` | Global app-infrastructure hooks (`useAuth`, `usePermissions`, `useSocket`) | Generic reusable UI hooks |
| `stores/` | Genuinely global client state | Feature-owned state |
| `types/` | Cross-cutting TypeScript types | Feature-specific DTOs |
| `config/` | Environment access, route map, app constants, feature flags | Runtime business logic |
| `styles/` | Design tokens and global CSS partials | Component-scoped styles |

Disambiguation rule: `shared/` is generic reuse. Top-level infra folders are singular runtime concerns for this app. If it would make sense in a completely different app, it belongs in `shared/`; if it is tied to this app's global runtime, it belongs in a top-level infra folder.

## 3. Feature Module Internal Architecture

Every module under `modules/` follows the same shape. Create only the subfolders a module actually needs.

```text
modules/projects/
├── components/
│   ├── project-card/
│   ├── project-list/
│   └── project-form/
├── hooks/
│   └── use-project-filters.ts
├── api/
│   ├── query-keys.ts
│   ├── queries/
│   │   ├── use-projects-query.ts
│   │   └── use-project-detail-query.ts
│   └── mutations/
│       ├── use-create-project-mutation.ts
│       ├── use-update-project-mutation.ts
│       └── use-delete-project-mutation.ts
├── services/
│   └── projects.service.ts
├── schemas/
│   └── project.schema.ts
├── types/
│   └── project.types.ts
├── store/
│   └── project-ui.store.ts
├── utils/
│   └── project.utils.ts
├── constants/
```

`services/*.service.ts` answer "how do I call this endpoint" and stay framework-free. `api/queries` and `api/mutations` answer "how does React consume this with TanStack Query" and own caching, invalidation, and optimistic updates.

### Core Rule: No Lateral Imports Between Modules

`modules/*` may depend on `shared/`, `lib/`, `providers/`, and top-level `hooks/`, `stores/`, `types`, `services`, and `config`. A module must never import from another module. If dashboard needs projects and contributors, that composition happens in a route file such as `routes/_appLayout/dashboard.tsx`.

The dependency graph must point from `routes/` to `modules/*` to `shared/` and infra, never sideways between modules.

## 4. Routing Architecture

TanStack Router file routes are the only routing surface. Route files compose feature exports into pages and can use route APIs for:

- `loader`/`beforeLoad` for SSR-compatible prefetching, redirects, and auth/role checks.
- `pendingComponent`, `errorComponent`, and `notFoundComponent` for route-level states.
- Pathless layouts such as `_authLayout.tsx`, `_appLayout.tsx`, and `_adminLayout.tsx` for shell reuse.
- Dynamic segments using TanStack Router file route syntax such as `$projectId` and `$username`.

Route files should stay thin. If JSX grows or behavior becomes domain-specific, extract it to the owning module.

## 5. Data Flow Architecture

**Read path:**

```text
Component (modules/*/components)
  -> feature query hook (modules/*/api/queries/use-x-query.ts)
    -> service function (modules/*/services/x.service.ts)
      -> axios instance (lib/axios)
        -> NestJS REST API
      <- normalized response/error
    <- typed DTO
  <- TanStack Query cache update
```

**Write path:**

```text
Form (React Hook Form + zod schema)
  -> mutation hook (modules/*/api/mutations/use-x-mutation.ts)
    -> service function -> axios -> NestJS
  <- success invalidates or updates module query keys
  <- optimistic update optional, rolled back on error
```

**SSR prefetch with TanStack Start:**

Route loaders can create or access the route-scoped query client, call `prefetchQuery`/`ensureQueryData` using the same service functions, and let TanStack Start dehydrate/hydrate the cache across the server/client boundary. Client components keep using the same query hooks whether data was loaded on the server or fetched after navigation.

**Real-time path:**

```text
lib/socket/socket-client.ts
  -> app-level realtime provider
    -> feature-owned envelope/cache adapters
      -> persisted server data reconciled into TanStack Query cache
```

One session-aware `/realtime` socket accelerates committed events for all
approved features. Real-time events and REST responses must converge into the
same TanStack Query cache; durable HTTP remains authoritative.

## 6. State Management Strategy

Rule: server-originated data that can be refetched belongs in TanStack Query. Pure client UI state belongs in local React state or Zustand. Never store server data in Zustand.

| Belongs to TanStack Query | Belongs to Zustand/local state |
|---|---|
| Projects, contributors, reviews, chat history, notifications list, kanban board data, discussion threads, roadmap data, user profiles | Sidebar collapsed, theme, modal stack |
| The `me`/current-user fetch | Kanban drag-in-progress local order |
| Anything fetched via `GET` or derived from it | Chat draft text, typing indicators, presence |
| Server-confirmed mutations | Multi-step form wizard state before submission |

Auth session gray area: `useCurrentUser()` is the source of truth. `stores/auth.store.ts` may hold only a minimal synchronous mirror for axios interceptors and route guards. That mirror is populated from the query result and never fetched independently.

## 7. API Architecture

- `lib/axios/axios-instance.ts`: configured instance with `baseURL` from `config/env.ts`, `withCredentials: true`, timeout, and default headers.
- `auth-interceptor.ts`: attaches `Authorization: Bearer <accessToken>` from the auth mirror if present.
- `refresh-token-interceptor.ts`: handles `401`, queues concurrent requests, calls `/auth/refresh` once, retries queued requests, and clears session on refresh failure.
- `error-interceptor.ts`: normalizes NestJS error responses into one app-level `ApiError`.
- `modules/*/services/*.service.ts`: thin raw HTTP functions, no React.
- `modules/*/api/queries/*`: TanStack Query read hooks only.
- `modules/*/api/mutations/*`: TanStack Query write hooks only.
- `modules/*/api/query-keys.ts`: centralized key factory per feature.
- `lib/query-client.ts`: query client factory/singleton usable by TanStack Start loaders and client providers.

Auth token strategy: short-lived access token is kept in memory only; refresh token lives in an httpOnly cookie set by the backend. On full page load, the auth provider silently refreshes or fetches `/auth/me` before protected UI is shown.

## 8. Component Architecture

- `shared/components/ui`: shadcn primitives only, no business logic.
- `shared/components/layout`: app chrome such as AppShell, Sidebar, Header, Footer, PageContainer.
- `shared/components/forms`: React Hook Form + shadcn wrappers.
- `shared/components/feedback`: Spinner, Skeleton, EmptyState, ErrorFallback, toast wiring.
- `shared/components/navigation`, `data-display`, `modals`, `icons`: feature-agnostic presentation helpers.
- `shared/components/providers`: reusable component-scoped providers.
- `providers/`: true app-wide providers mounted once in `routes/__root.tsx`.

A component used by exactly one feature lives in that feature. Promote to `shared/` only after real reuse appears.

TanStack Start does not use React Server Component boundaries. Keep route loaders and server-only code out of browser-only modules, and keep browser APIs inside components/hooks that run in the browser.

## 9. Import Strategy

Use absolute imports for cross-layer references:

```jsonc
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"],
      "@/modules/*": ["./src/modules/*"],
      "@/shared/*": ["./src/shared/*"],
      "@/lib/*": ["./src/lib/*"]
    }
  }
}
```

- Within a module, relative imports between siblings are fine.
- Across modules/layers, use aliases.
- External consumers import features through the module root barrel only.
- Deep imports into another module's internals are forbidden.
- Enforce boundaries with ESLint, preferably `no-restricted-imports` or `eslint-plugin-boundaries`.

## 10. Naming Conventions

| Item | Convention | Example |
|---|---|---|
| Files | kebab-case | `project-card.tsx`, `use-projects-query.ts` |
| Folders | kebab-case; module folders are plural resource names | `contributors/`, `data-display/` |
| Route files | TanStack Router file route syntax | `_authLayout.tsx`, `profile.$username.tsx`, `$projectId.kanban.tsx` |
| Components | PascalCase export matching kebab-case filename | `project-card.tsx` -> `ProjectCard` |
| Hooks | camelCase export, `use-` prefixed file | `use-project-filters.ts` -> `useProjectFilters` |
| Stores | `*.store.ts`, export `useXStore` | `project-ui.store.ts` -> `useProjectUiStore` |
| Types/interfaces | PascalCase, no `I`/`T` prefix | `ProjectCardProps`, `ProjectStatus` |
| Constants | `UPPER_SNAKE_CASE` for primitives, camelCase for config objects | `MAX_FILE_SIZE_MB`, `queryConfig` |
| Env vars | `VITE_` only for browser-exposed values; access through `config/env.ts` | `VITE_API_URL`, `VITE_SOCKET_URL` |

Use `*Dto`/`*Response` for API payloads, `*Props` for component props, and `*Filters` for query params.

## 11. Barrel Exports

Use barrels for:

- Each feature module root, for example `modules/projects/index.ts`.
- Category-level shared component barrels where they improve imports.

Avoid barrels for:

- Single-component folders with no import benefit.
- A monolithic `shared/index.ts`.
- Barrels that mix browser-only exports with server/loader-only utilities.

## 12. Code Standards

- Component JSX over roughly 150-200 lines should be split.
- Hooks should do one thing: one query, one mutation, or one piece of derived UI logic.
- Service/util functions stay small and pure.
- Every folder under `modules/*` has exactly one owning feature.
- Dependency direction: `routes/` -> `modules/*` -> `shared/` + top-level infra -> `lib/`.
- Components/hooks never parse raw backend error shapes.
- Use shared loading/empty/error components instead of one-off text states.
- Prefer route pending/error components for route transitions and TanStack Query flags for client interactions.

## 13. Best Practices

- Enforce module boundaries with ESLint.
- Derive types from Zod schemas where practical.
- Centralize query keys per feature.
- Type Axios responses against shared envelopes.
- Standardize loading, empty, and error UI through `shared/components/feedback`.
- Run ESLint, TypeScript, and Vitest in CI.
- Co-locate tests next to source where practical.
- Add Playwright E2E specs for critical flows: auth, project creation, kanban DnD, chat, AI assistant.

## Common Mistakes To Avoid

- Feature modules importing each other directly.
- Moving components to `shared/` before real reuse exists.
- Storing server data in Zustand for convenience.
- Inline axios calls in components.
- Deep relative imports across layers.
- Giant barrel files that hide circular dependencies.
- Parsing raw backend error shapes in multiple places.
- Hand-typing query keys inline.

## Long-Term Scalability

- Generate frontend DTOs/services from the NestJS OpenAPI spec with `openapi-typescript` and `orval`.
- Split into a Turborepo/Nx monorepo only when a second frontend or package boundary justifies it.
- Add Storybook once shared component count grows.
- Introduce `config/feature-flags.ts` before staged rollouts become urgent.
- Centralize analytics in `services/analytics.service.ts`.
- Map CODEOWNERS to `modules/*` when team ownership expands.
